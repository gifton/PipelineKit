#### Important (Should Fix)

- **R02-I1 — Accepted finite queue timeouts can trap during admission.** `Sources/PipelineKitResilienceCircuitBreaker/BulkheadMiddleware.swift:142` checks only `isFinite`, while `:238` unconditionally constructs `.seconds(timeout)` on the contended queue path. Finite values such as `1e30` and `-1e30` pass initialization but exceed `Duration`'s signed 128-bit attosecond range. Swift 6.2's conversion performs a checked scaled multiplication, so these inputs trap instead of producing the wrapper's queue error. This also creates a concrete queue-disabled regression: with capacity occupied, `.queue`, `maxQueueSize: 0` and a huge positive finite timeout, old code rejected before converting the timeout; new code converts before the gate can report `full`. Extreme negative finite values likewise violate the newly tested nonpositive no-wait behavior. This is source-established, not a claimed crash-probe result. [Swift 6.2 conversion](https://github.com/swiftlang/swift/blob/swift-6.2-RELEASE/stdlib/public/core/Duration.swift#L141-L166).

  Choose and document a supported positive timeout range, and validate it before admission can execute. If finite nonpositive values retain the no-wait policy, normalize them to `.zero` before conversion. The positive bound must also leave room for the default sleeper's immediate deadline construction: the unchanged gate calls `clock.sleep(for:)` at `Sources/PipelineKitResilienceFoundation/Admission/AdmissionGate.swift:64`, which advances `now`, and `ContinuousClock.Instant.advanced(by:)` adds the duration. Merely accepting anything that converts to `Duration`, or capping at its maximum, is insufficient. [Clock sleep](https://github.com/swiftlang/swift/blob/swift-6.2-RELEASE/stdlib/public/Concurrency/Clock.swift#L98-L105), [ContinuousClock advancement](https://github.com/swiftlang/swift/blob/swift-6.2-RELEASE/stdlib/public/Concurrency/ContinuousClock.swift#L129-L131). Add focused boundary cases for the chosen positive limit/rejection policy and extreme negative values, with free/occupied capacity and queue limits 0/1. This finding concerns R02's new conversion and validation; it does not reopen unrelated existing duration debt or require changing R01's ownership algorithm.
