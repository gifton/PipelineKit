# Upgrading from 0.5.4 to 0.6.0

This guide is for applications that depend on PipelineKit 0.5.4 and are moving to 0.6.0. It
lists every change that needs a code edit, a configuration review, a data migration or a
deployment step, grouped by module. The [CHANGELOG](../../CHANGELOG.md#060---2026-11-07) has the
complete list of changes, including those that need no action.

Every Swift example in this guide is compiled against the public modules in Debug and Release
by CI; see [How this release was verified](#how-this-release-was-verified). The instructions
for `PipelineKitTestSupport` have no examples and are not part of that check.

## Before you upgrade

### Dependency range

Depend on `"0.6.0"..<"0.7.0"`. Under [VERSIONING.md](../../VERSIONING.md) a later minor
release may break source, and `from: "0.6.0"` would accept it. The Swift 6.2 and Apple OS 26
deployment floors are unchanged in 0.6.0; 0.6.1 lowers the deployment floors
([platform support](../platform-support.md)).

### Stored data and deployment order

Four kinds of data written by 0.5.x need more than a recompile. Plan these before deploying.

| Data | What to do | Details |
| --- | --- | --- |
| Cache contents, including persistent and distributed backends | Invalidate all of them. The key namespace changed, so old entries are never matched again. | [Invalidate existing cache contents](#invalidate-existing-cache-contents) |
| Commands encrypted by `CommandEncryptor` in 0.5.x | Recover each command with the 0.5.x consumer and its keys, then encrypt it again with 0.6.0. Do this before removing the old consumer, the original command data or the old keys. | [Commands encrypted by 0.5.x](#commands-encrypted-by-05x) |
| Compressed payloads | Read payloads stored under the old format labels through the legacy decoder. The 0.5.x utility returned payloads of 1 to 100 bytes as unmarked raw bytes; those need application metadata or regeneration. | [Compression format names and stored labels](#compression-format-names-and-stored-labels), [Decompression requires an output limit](#decompression-requires-an-output-limit) |
| Distributed rate-limit counters | Counters stored under the former raw identifiers are not read by 0.6.0, which uses scope-prefixed keys. Old and new processes count independently unless the rollout is coordinated. | [Rate limiting: distributed store keys](#rate-limiting-distributed-store-keys) |

Deployment order in a mixed-version system:

- **Compression:** deploy readers that recognize the new stored labels before any process
  writes them.
- **Distributed rate limits:** quiesce 0.5.x callers and let their active accounting windows
  expire before enabling 0.6.0 callers on the same store, or migrate the counts under a
  procedure specific to your store.
- **Encryption:** finish and verify the re-encryption before retiring the 0.5.x consumer.

## Core pipeline

### Cancellation is reported as PipelineError.cancelled

`StandardPipeline`, `AnyStandardPipeline`, and `DynamicPipeline` check task
cancellation at entry, between middleware, and before the handler, including
empty and cached chains. Their outward cancellation error is
`PipelineError.cancelled(context:)`. A handler's native `CancellationError` is
normalized to that case; an existing typed cancellation keeps its context.
An unrelated thrown error retains its identity even if the task is cancelled.
These boundaries do not preempt arbitrary handlers or replace successful results
after work has settled.

`CommandContext.getCancellationReason()` returns diagnostic metadata. The pipelines record
`.userCancellation` only if no more specific reason is already present. Reusing
a context with an old reason does not cancel a live task.

The throwing acquisition APIs on `SimpleSemaphore`, `AsyncSemaphore`, and
`BackPressureSemaphore` now throw `PipelineError.cancelled`. The timed Boolean
`AsyncSemaphore` overload still returns `false` on cancellation. Permit ownership
and settlement behavior are unchanged. Direct APIs outside these boundaries,
including admission gates and test helpers, may still throw native cancellation.

When accepting errors from both library pipelines and other async operations,
recognize both cancellation types:

```swift
import PipelineKit

func isCancelledExecution(_ error: any Error) -> Bool {
    if error is CancellationError { return true }
    if case .cancelled = error as? PipelineError { return true }
    return false
}
```

### Builders keep every stage

Builder additions from plain, named, array and explicit-order APIs now compose into one
sequence. Explicit effective priority and stable ties survive construction. In 0.5.4 a
builder that mixed these styles could drop stages. Security stages that were dropped can now
reject commands, so add the required
[command conformances](#validation-and-sanitization-need-explicit-conformances) before
exercising such a route.

### Memory-pressure monitoring is async

`MemoryPressureResponder.startMonitoring()` and `stopMonitoring()` are now
explicitly async. Calls from outside the actor already use `await`:

```swift
import PipelineKit

let memoryResponder = MemoryPressureResponder()
await memoryResponder.startMonitoring()
await memoryResponder.stopMonitoring()
await memoryResponder.startMonitoring()
await memoryResponder.stopMonitoring()
```

An external start waits for observer registration; an external stop invalidates
the run, cancels it, removes its exact notification token, and waits for its
owned work to settle. Repeated stops also join a retiring run. A new generation
waits for its predecessor to settle before registering or sampling. Releasing
an idle responder cancels its work without a background task retaining it.
The singleton `MemoryPressureDetector` forwards the same shutdown behavior.

A handler may stop its own run without waiting for itself. If that handler
then starts monitoring again, start queues the successor and returns before
registration; registration waits for the old callback to finish. External
callers retain the normal awaited-registration and settlement guarantees.
Handlers that ignore cancellation can delay external stop or restart.
Memory thresholds and the existing available-memory estimate are unchanged.

### MemoryProfiler is removed

`MemoryProfiler`, its nested snapshot/allocation/report types, `MemoryPattern`, and
the global `memoryProfiler` have been removed. Remove those references from clients.
There is no replacement profiling API. Memory-pressure detection and
memory-pressure response remain separate APIs.

### Smaller behavior changes

None of these needs a code change in a typical application.

- **NextGuard diagnostics.** Middleware that throws without calling `next()` no longer
  produces the debug-only "deallocated without calling next()" warning.
  `NextGuardWarningSuppressing` is now needed only by middleware that returns a result
  without calling `next()` on a normal path, such as a cache hit. The protocol is still
  public. Its conformance was removed from eleven middleware that reject by throwing:
  `BackPressureMiddleware`, `CircuitBreakerMiddleware`, `RateLimitingMiddleware`,
  `EnhancedRateLimitingMiddleware`, `PartitionedBulkheadMiddleware`, `HealthCheckMiddleware`,
  `ValidationMiddleware`, `SecurityPolicyMiddleware`, `AuthenticationMiddleware`,
  `AuthorizationMiddleware` and `MockAuthenticationMiddleware`. Only code that checks
  `is any NextGuardWarningSuppressing` can observe this. The cache middleware and
  `BulkheadMiddleware` keep the conformance.
- **Warning suppression scope.** The static `withoutWarnings` method on `NextGuard` is
  task-scoped: it covers guards created by its closure and that closure's child tasks.
  Concurrent changes to `NextGuardConfiguration.shared` are independent of that scope.
  Warning handlers run after the configuration lock is released.
- **Context callbacks.** Context descriptions, metadata getters, and retired-value
  destruction execute outside the context storage lock, so a callback can read or mutate the
  same context. Snapshot storage capture is atomic, but callbacks may mutate the context
  afterward. A snapshot is not a transaction across arbitrary user-supplied getters.

## Security

### Validation and sanitization need explicit conformances

Commands used with `ValidationMiddleware()` must conform to `ValidatableCommand`, and
commands used with `SanitizationMiddleware()` must conform to `SanitizableCommand`. The
default policy is `.required`. Missing conformance throws
`SecurityCapabilityError.missingValidation` or `.missingSanitization` before the next stage
runs.

The old extension-only hooks did not dispatch to command-specific implementations from a
generic pipeline. Move the implementation into an explicit conformance and use these
async signatures:

- `func validate() async throws`
- `func sanitize() async throws -> Self`

There are no no-op witnesses. `validateAsync()`, `sanitizeAsync()`, `requiresValidation`,
`requiresSanitization` and `hasSensitiveFields` have been removed. Update direct callers to
`try await command.validate()` or `let replacement = try await command.sanitize()`.
Validation and sanitization errors propagate unchanged. Sanitization middleware passes the
returned command downstream; immutable caller values remain unchanged.

```swift
import Foundation
import PipelineKit
import PipelineKitSecurity

enum PostInputError: Error { case emptyTitle }

struct CreatePostCommand: ValidatableCommand, SanitizableCommand {
    typealias Result = String
    let title: String

    func validate() async throws {
        guard !title.isEmpty else { throw PostInputError.emptyTitle }
    }

    func sanitize() async throws -> Self {
        Self(title: title.trimmingCharacters(in: .whitespacesAndNewlines))
    }
}

struct CreatePostHandler: CommandHandler {
    func handle(_ command: CreatePostCommand, context: CommandContext) async throws -> String {
        command.title
    }
}

func makePostPipeline() async throws -> StandardPipeline<CreatePostCommand, CreatePostHandler> {
    let builder = PipelineBuilder(handler: CreatePostHandler())
    // Equal effective priority retains insertion order: sanitize, then validate.
    await builder.with(SanitizationMiddleware(), order: .validation)
    await builder.with(ValidationMiddleware())
    return try await builder.build()
}
```

Intrinsic priorities still put validation (200) before sanitization (300). The explicit
order above makes validation inspect normalized input. Choose that ordering deliberately
for your command's contract. Sanitization is application-defined transformation, not a
universal injection defense.

For a pipeline that intentionally handles both capable and unrelated commands, opt out of
required conformance explicitly with `ValidationMiddleware(requirement: .ifPresent)` and/or
`SanitizationMiddleware(requirement: .ifPresent)`. Present capabilities still execute and
still propagate their errors. Avoid applying this opt-out to routes that require validation
or sanitization of every command.

`SecurityValidatable` remains the separate security-policy protocol; `EncryptableCommand`
remains the separate encryption-middleware protocol. Neither substitutes for the new
capabilities.

### Command encryption takes complete Codable commands

`CommandEncryptor.encrypt` and `decrypt` now require `T: Command & Codable`. Encode all
state required to reconstruct your command. The encryptor JSON-encodes the complete command,
seals it with AES-GCM-256, and reconstructs a new `T` by opening and decoding that payload.
The `Command` extension hooks `sensitiveFields` and `updateSensitiveFields` are removed, and
the encryptor no longer calls them.

`EncryptedCommand<T>` contains only `encryptedData`, `keyIdentifier`, and `algorithm`.
`T` is a phantom type; no command, redacted shell, closure, or plaintext reference is retained.
Remove uses of `originalCommand` and replace the old initializer with the three-field one:

```swift
import Foundation
import PipelineKit
import PipelineKitSecurity

struct StoredCommand: Command, Codable {
    typealias Result = Void
    let accountIdentifier: String
    let payload: Data
}

func storeAndRestore(
    _ command: StoredCommand,
    using encryptor: CommandEncryptor
) async throws -> StoredCommand {
    let encrypted = try await encryptor.encrypt(command)
    // Persist or transmit these three fields; retain the expected command type separately.
    let restoredEnvelope = EncryptedCommand<StoredCommand>(
        encryptedData: encrypted.encryptedData,
        keyIdentifier: encrypted.keyIdentifier,
        algorithm: encrypted.algorithm
    )
    return try await encryptor.decrypt(restoredEnvelope)
}
```

Decryption accepts only the exact `AES-GCM-256` algorithm label. Cryptographic
authentication and Codable failures propagate instead of returning a retained original
command.

### KeyStore publishes one key snapshot

Every `KeyStore` conformer must replace its separate `currentKey` and `currentKeyIdentifier`
requirements with `var currentKeySnapshot: EncryptionKeySnapshot? { get async }`. Capture the
key and identifier together under the store's isolation; never assemble a pair from independent
async reads. Keep key lookup, storage and expiration methods. For example, this in-memory
teaching store publishes a pair in the same actor turn as its key write:

```swift
import Foundation
import PipelineKitSecurity

actor ExampleVersionedKeyStore: KeyStore {
    private var keys: [String: SendableSymmetricKey] = [:]
    private var dates: [String: Date] = [:]
    private(set) var currentKeySnapshot: EncryptionKeySnapshot?

    func key(for identifier: String) -> SendableSymmetricKey? { keys[identifier] }

    func store(key: SendableSymmetricKey, identifier: String) {
        keys[identifier] = key
        dates[identifier] = Date()
        currentKeySnapshot = EncryptionKeySnapshot(key: key, identifier: identifier)
    }

    func removeExpiredKeys(before cutoff: Date) {
        for (identifier, date) in dates where date < cutoff && identifier != currentKeySnapshot?.identifier {
            keys.removeValue(forKey: identifier)
            dates.removeValue(forKey: identifier)
        }
    }
}
```

Use a fresh identifier for each stored key version and supply only 256-bit keys. Encryption
captures one immutable pair; another encryptor rotating the same store does not change the
identifier attached to an already captured key. Old keys remain available until the store
explicitly expires them. Missing or expired keys fail with `.keyNotFound`; a key of the wrong
size fails with `.invalidKey`.

### Commands encrypted by 0.5.x

The 0.5.x partial-field ciphertext format is incompatible with complete-command decoding.
Migrate before removing the old consumer or losing its original command objects: use that
consumer and its keys to recover the complete application command, then re-encrypt it through
the new Codable API. The old generic hooks could seal an empty JSON object, so old ciphertext
alone is not evidence that lost command fields can be recovered. Keep both the original
command data and required old keys until migration is verified; if either is already lost,
recovery may be impossible. Migration validation should record counts and pass/fail results,
never synthetic or real plaintext.

### Encrypted result fields

This section concerns `EncryptionMiddleware` and its `EncryptionService`, which are separate
from `CommandEncryptor`. `EncryptionService` keeps its typed `encrypt`, `decrypt`, and
`validate` methods. Services that support custom result objects, arrays, or envelopes
without type hints should also conform to `SerializedPlaintextDecrypting` and implement
`decryptSerializedPlaintext(_:)`. This method must authenticate the payload and
return its exact serialized bytes. It must throw on authentication failure.
Share the authenticated opening operation with typed decryption; do not decode
as `Data.self` or deserialize and re-encode the plaintext.

The [field encryption example](../guides/security-best-practices.md#field-level-encryption)
shows a conforming AES-GCM service. Existing typed-only services continue to
handle recognized String, Int, Double, Bool, Date, and Data hints. Fields that
need serialized bytes fail explicitly when the service lacks the new capability.
With partial decryption enabled, only successful fields reach
`withDecryptedData`; inspect `decryption.failedFields` for failures.

For custom JSON hints, middleware supplies `TypedData`. Choose the expected type
from your application's schema and decode that type explicitly:

```swift
import Foundation
import PipelineKitSecurity

struct AccountPayload: Codable, Sendable {
    let accountID: String
    let labels: [String]
}

func decodeAccountField(_ value: DecryptedValue) throws -> AccountPayload {
    guard let serialized = value.get(as: TypedData.self) else {
        throw EncryptionError.decryptionFailed("Expected serialized account field")
    }
    return try serialized.decode(as: AccountPayload.self)
}
```

`typeHint` and `encodingFormat` remain **untrusted, unauthenticated metadata** in
the current AES-GCM envelope. Do not use either as authorization or proof of the
expected schema. 0.6.0 does not add authenticated associated data or change
the ciphertext format.

An absent hint, or an unknown hint with a non-JSON encoding, produces serialized
`Data` bytes. This differs from decoding a value originally encoded as `Data`:
JSON encodes that value as a base64 string. An old hintless envelope containing
encoded Data therefore returns the JSON string bytes, including its quotes.
Decode using the known original schema; do not infer the type from byte contents.

Encryption middleware preserves downstream handler errors. Its own encryption and
decryption failures are thrown as `PipelineError.encryption(reason:)`; see
[Typed rejection errors](#typed-rejection-errors). Recognized native or
typed cancellation is propagated as typed cancellation before crypto-failure
mapping; partial-decryption mode cannot turn cancellation into success.

### Automatic security validation counts nested content

Strict reflection-based `SecurityPolicyMiddleware` validation now charges supported leaves
in arrays, nested values, present optionals, and inherited stored fields. Commands that
previously bypassed size or string restrictions through these shapes may now be rejected.

The size estimate measures logical reflected content: String UTF-8 bytes, Data bytes, and
`MemoryLayout<Any>.size` per supported scalar. Supported scalars are Bool, Int/UInt and their
8/16/32/64-bit variants, Float, Double, UUID, and Date. Container overhead and absent optionals
contribute zero. Opaque leaves and content hidden by custom mirrors are not measured.
This estimate is neither a serialized size nor a process-memory budget.

Repeated acyclic references count once per occurrence. Reflected reference cycles now fail
with the existing security-policy validation-failed error. Commands with intentional cycles
can implement `SecurityValidatable`; that validator takes precedence and must enforce the
application's complete policy. The existing non-strict reflection bypass is unchanged.

Size validation stops at the first excess. The error reports the observed sum rather than
the size of unvisited content; an overflowing sum rejects and reports `Int.max`.

### Audit logging and truncation

Truncation uses Swift Characters and returns empty for nonpositive maxima; overlong suffixes
are themselves truncated to the maximum. `InMemoryAuditLogger(capacity: 0)` retains no events
and counts drops; negative capacity violates a precondition. Standard `userID`/`sessionID`
metadata now appears in the production audit identity whitelist. No arbitrary sensitive
metadata is added to that whitelist.

### If you copied the security guide's wrappers

The [security guide](../guides/security-best-practices.md) now registers error sanitization
and security metrics outside authentication using explicit equal-priority insertion order.
Audit masking filters the complete enriched metadata and suppresses task-local audit
enrichment only while forwarding the filtered event. Applications that copied the 0.5.4
examples should update both the wrappers and their registration order.

## Resilience

Deadlines remain cooperative throughout this module: they do not preempt arbitrary handlers,
and admitted work keeps its resources until it settles.

### Removed bulkhead API

The compatibility APIs deprecated in 0.5.4 are removed:

| Removed API | Replacement |
| --- | --- |
| `BulkheadMiddleware.IsolationMode.tagged` | `PartitionedBulkheadMiddleware` with declared partitions and `allowBorrowing: false` for separate capacity. Use `.semaphore` when one shared limit is intended. |
| `Configuration.maxBorrowPercentage` and its initializer parameter | `reservedCapacityPercentage`; the value still means the lender's reserved, non-lendable fraction. |

The tagged mode's automatic `bulkheadTag` metadata is removed with that mode.
Applications needing a diagnostic tag should write it explicitly. The
[partition example](../guides/resilience-patterns.md#multi-tenant-workloads)
shows the replacement extractor, which receives command and context.

### Queue and admission timeouts

One rule now applies to `BulkheadMiddleware.Configuration.queueTimeout`,
`PartitionedBulkheadMiddleware.PartitionConfig.queueTimeout`, the
`PipelineOptions.backPressureStrategy` value `.error(timeout:)`, and semaphore admission
waits:

- `nil` means no admission deadline, subject to the strategy's capacity rejection rules.
- Finite nonpositive values permit immediate admission only.
- Positive values must be finite and no greater than 86,400 seconds (24 hours).
- NaN, either infinity, and larger positive values fail a configuration precondition. For
  bulkheads this applies even when the queue has `maxQueueSize: 0` or `queueSize: 0`.

The 24-hour cap is a deliberate PipelineKit policy, not Swift Duration's intrinsic range
limit. It applies to admission waits only; see [Numeric input rules](#numeric-input-rules).

Check configurations that previously supplied nonfinite or longer deadlines. Using `nil`
with application-managed cancellation is one option, but `nil` is an unbounded wait: it does
not preserve the old finite deadline. An admitted handler continues to own its capacity
until it settles; there is no hard handler deadline or preemptive cancellation.

`ConcurrentPipeline` now applies the `.error(timeout:)` deadline to ordinary execution.
In 0.5.4 that configured admission deadline was ignored, so a configuration that never
timed out can now throw the existing back-pressure timeout error. The explicit
`execute(_:context:timeout:)` overload overrides the configured deadline. Both deadlines
cover waiting for admission only. The existing back-pressure timeout and queue-full error
cases are retained.

For bulkheads, finite nonpositive values normalize to zero without converting their
magnitude, so even very large negative values permit immediate free capacity and return the
existing queue-timeout error if a wait would be required. Positive values round to the
nearest attosecond; a tiny positive value rounding to zero has the same no-wait behavior.
Positive values that remain nonzero return the existing full-queue error when capacity is
occupied and the queue limit is zero.

Partitioned bulkheads also validate positive partition capacities, nonnegative queue sizes,
and a finite reserved-capacity percentage in `0...1` before creating admission gates.

### Pipeline capacity and outstanding limits

Nil `PipelineOptions.maxConcurrency` and `maxOutstanding` now mean unlimited, including
the `.unlimited()` preset. A finite outstanding bound still applies when concurrency is
unlimited. `PipelineCapacityStats.maxOutstanding` preserves nil; its nonoptional
`maxConcurrency` uses `Int.max` to represent unlimited, and utilization is zero for
unlimited concurrency.

A finite `maxOutstanding` now bounds executing plus queued work for every overload
strategy. Increase it explicitly if an application relied on the former suspend
allowance of twice the configured limit or timed-error queueing beyond that limit.

| Strategy | At the outstanding limit |
| --- | --- |
| `.suspend` | Reject with queue-full; wait for a permit only while queue capacity exists. |
| `.error(timeout:)` | Nil or positive timeouts reject with queue-full; nonpositive timeouts retain immediate-only timeout rejection. |
| `.dropNewest` | Reject the incoming operation as dropped. |
| `.dropOldest` | Replace the earliest-enqueued waiter if one exists and the replacement fits queue memory; otherwise reject. |

Eviction never cancels an already executing operation. Oldest eviction uses insertion
order independently of service priority or wall-clock timestamps. Service still selects
higher-priority waiters first, with FIFO order within a priority. A rejected replacement
leaves the existing queue and its permit ownership intact. Immediate-only admission
timeouts do not enqueue or evict.

`BackPressureMiddleware` and `ConcurrentPipeline` return their owned capacity before
an awaited execution returns or throws. Sequential calls therefore remain usable at
an outstanding limit of one, including after handler failures.

Pipeline options no longer inherit the semaphore's separate five-minute stale-waiter
cleanup. Direct callers of the public `BackPressureSemaphore` initializer retain its
`waiterTimeout` parameter and default, and its nil outstanding limit still defaults
to ten times concurrency; any resolved finite limit is strict.

### Typed rejection errors

Update catches that previously inspected generic middleware names or raw crypto
errors generated by middleware:

| Producer | Error now emitted |
| --- | --- |
| Breaker rejection | `PipelineError.circuitBreakerOpen(resetTime:)` |
| Ordinary or partitioned bulkhead rejection | `PipelineError.bulkheadRejected(reason:)` |
| Ordinary or partitioned bulkhead queue deadline | `PipelineError.bulkheadTimeout(timeout:queueTime:)` |
| Encryption middleware's encryption/decryption failure | `PipelineError.encryption(reason:)` |

An open breaker's `resetTime` is the deadline observed when it rejected the call.
A busy half-open breaker has no known reset deadline and returns `nil`.
The redundant bulkhead error factories that shadowed the typed enum cases are
removed; the typed cases retain their construction syntax.

### What retry, health and breakers count as failure

Retry, resilient retry, health, and breaker middleware recognize both direct
cancellation types, `PipelineError.cancelled` and native `CancellationError`, before
invoking custom error predicates. Cancellation is
never retryable or a service failure, even if a custom predicate returns `true`.
Retry loops check cancellation before the next attempt and during backoff.

By default, health and breakers exclude these direct typed `PipelineError` cases:

| Category | Cases |
| --- | --- |
| Command and security policy | `validation`, `authentication`, `authorization`, `securityPolicy` |
| Rate and admission | `rateLimitExceeded`, `circuitBreakerOpen`, `bulkheadRejected` |
| Legacy resilience categories | `resilience(.bulkheadFull)`, `resilience(.circuitBreakerOpen)` |
| Back pressure | `backPressure(.queueFull)`, `backPressure(.commandDropped)`, `backPressure(.memoryPressure)` |

Ignored outcomes are neither successes nor failures: they do not reset health
streaks or add samples to its health window. They can still emit an execution
failure event. Timeouts and unknown downstream failures still count by default.
Existing time-window expiry and recovery rules remain in effect.

Custom predicates can override classification of noncancellation errors.
Health configuration adds an optional `errorEvaluator` parameter:

```swift
import PipelineKit
import PipelineKitResilience

let healthPolicy = HealthCheckMiddleware.Configuration(
    errorEvaluator: { error in
        // This application's explicit policy ignores its own validation errors.
        if case .validation = error as? PipelineError { return false }
        return true
    }
)
_ = healthPolicy
```

Retry and circuit-breaker policies classify the four typed `PipelineError` timeout cases
by their enum cases. Other `PipelineError` values do not become timeouts because their
descriptions or payloads contain the word `timeout`. Remaining cases, including `.wrapped`
and `.retryExhausted`, follow each policy's unknown-error behavior and are not recursively
unwrapped. Applications that intentionally classify wrapped errors should supply an
`errorEvaluator` to the relevant middleware configuration and inspect the wrapper
explicitly. Retry and breaker policies retain their existing description-based timeout
fallback for foreign errors; health treats unknown errors as failures by default.

### Retry time budget and HTTP status extraction

`RetryMiddleware.Configuration.maxRetryTime` is a monotonic budget measured from
execution entry. It controls admission of the initial attempt, later attempts, and
backoff. Nil disables the time budget; zero admits no attempt. `maxAttempts` continues
to count retries in addition to the initial attempt.

Backoff is limited to the remaining budget. The middleware rechecks the budget after
policy/event callbacks before beginning more work. A handler admitted before expiry
can complete afterward: success is returned, and a failure keeps its original identity
without another retry. Exhaustion before any attempt throws
`RetryError.maxRetryTimeExceeded`; after a failure it returns that last error.
Callback or handler work that does not return can delay settlement beyond the budget.

```swift
import PipelineKitResilience

let budgetedRetry = RetryMiddleware(configuration: .init(
    maxAttempts: 2,
    strategy: .fixed(delay: 0.1),
    maxRetryTime: 0.25
))
_ = budgetedRetry
```

The HTTP factory now requires a status-code extractor. Its former private error type
could not be supplied by consumers. Adapt application or transport errors explicitly:

```swift
import PipelineKitResilience

struct ServiceHTTPFailure: Error {
    let statusCode: Int
}

let httpRetry = RetryMiddleware.forHTTPStatusCodes([429, 502, 503]) { error in
    (error as? ServiceHTTPFailure)?.statusCode
}
_ = httpRetry
```

An unknown or unlisted status does not retry. Native `CancellationError` and
`PipelineError.cancelled` bypass the extractor and all retry predicates.

### Timeout options

Remove `cancelOnTimeout:` and `gracePeriodBackoff:` from timeout configuration.
Both were ignored. Replace the adaptive-grace initializer with an explicit fixed
grace period:

```swift
import PipelineKitResilience

let timeoutPolicy = TimeoutMiddleware(configuration: .init(
    defaultTimeout: 2,
    gracePeriod: 0.25
))
_ = timeoutPolicy
```

The initial deadline begins a configured grace period; expiry requests cooperative
cancellation and waits for owned work to settle. A zero grace period requests
cancellation at the initial deadline. Grace recovery is recorded from the outcome of
that invocation, so sequential and concurrent executions do not share tracker state.
A suspended grace notification cannot postpone the grace deadline. The notification
remains owned work and is cancelled/joined when its scope ends.

Caller cancellation and timeout-owned expiry are separate outcomes. Handler error identity
is preserved when settling caller cancellation; a deadline that wins retains its
timeout outcome while joining the losing operation. Neither a slow handler nor a slow
diagnostic callback is a hard wall-clock bound on return.
Handler-originated `TimeoutError` values, including nested timeout failures, retain
their original case and payload without triggering the outer timeout diagnostics.

Standalone `GracePeriodBackoff` remains a duration calculator. It does not configure
`TimeoutMiddleware`. Existing fixed-grace, per-command timeout, resolver, and timeout
handler APIs remain available.

### Rate limiting: scope, priority, status and reset

**Scope.** `RateLimiter(scope: .global)` now applies one budget to all supplied identifiers
in every strategy: token bucket, sliding window, fixed window, leaky bucket, adaptive,
distributed, and priority based. Keep passing the original user/IP/command identifier; do
not pre-encode a key. Admission, status and keyed reset normalize it the same way. For
example, after a one-request global budget admits `"A"`, `"B"` is denied and its status
reports the same remaining budget. Applications that relied on the previous separate
per-caller budgets must select `.perUser`, `.perIP` or `.perCommand` explicitly.

**Priority.** `RateLimiter.allowRequest(identifier:cost:priority:)`,
`getStatus(identifier:priority:)`, and `reset(identifier:priority:)` accept a priority that
defaults to `.medium`. `EnhancedRateLimitingMiddleware` passes its extracted priority
to both admission and rejection-status lookup. For `.priorityBased`, each configured
priority has its own budget; a missing priority is denied with zero limit/remaining.
Other rate strategies retain their existing cost and admission policies.

**Status and reset throw.** `getStatus` and `reset` are now `async throws`. Add `try` to
existing calls:

```swift
import PipelineKitResilience

let priorityLimiter = RateLimiter(strategy: .priorityBased(limits: [
    .medium: .init(maxRequests: 10, windowSize: 60),
    .high: .init(maxRequests: 20, windowSize: 60)
]))
_ = try await priorityLimiter.allowRequest(identifier: "customer", priority: .high)
let highStatus = try await priorityLimiter.getStatus(identifier: "customer", priority: .high)
try await priorityLimiter.reset(identifier: "customer", priority: .high)
try await priorityLimiter.reset()
_ = highStatus
```

A distributed status lookup propagates the store's error, including cancellation, instead
of returning a fabricated empty count or available quota. A negative count from the store
throws a validation error. An unavailable store therefore no longer reads as an unused
budget; `RateLimitStatusContractTests` covers this.

`SecureCommandDispatcher.getRateLimitStatus(userID:commandType:)` also requires `try await`.
Its optional result is `nil` only when no rate limiter is configured; a failed status
lookup throws.

Keyed reset uses the same effective scope and priority key as admission and status. A nil
identifier clears every local identifier and priority. In global scope, identifiers
refer to the shared budget.

Distributed keyed reset awaits `DistributedRateLimitStore.reset(key:)` and propagates
the original store error. Global reset-all can reset its one known global key.
Non-global reset-all requires `ResettableDistributedRateLimitStore.resetAll(keyPrefix:)`;
otherwise it throws `RateLimitResetError.resetAllUnsupported`. Existing store conformers
remain valid for admission, status, and keyed reset without adopting the new capability.
`InMemoryRateLimitStore` implements the capability.

The prefix identifies one PipelineKit scope in the backing store's budget namespace.
Adapters must apply their own namespace framing consistently to normal keys and reset
prefixes. Reset-all must reach keys written by other limiter instances; clearing only
locally observed identifiers is insufficient. A reset orders against concurrent
admissions according to the backing store's operations and does not prevent future
admissions.

### Rate limiting: distributed store keys

All four scopes use separate internal namespaces. A distributed store receives these
exact keys, with the caller's complete supplied string appended verbatim in non-global scopes:

| Scope | Key passed to `DistributedRateLimitStore` |
| --- | --- |
| `.global` | `pipelinekit:rate-limit:v1:global` |
| `.perUser` | `pipelinekit:rate-limit:v1:user:` + supplied identifier |
| `.perIP` | `pipelinekit:rate-limit:v1:ip:` + supplied identifier |
| `.perCommand` | `pipelinekit:rate-limit:v1:command:` + supplied identifier |

Treat those incoming keys as opaque in the store. A supplied string that already resembles
an internal key remains caller data and gets its scope prefix; it is never decoded or stripped.
Two distributed limiter instances using the same store budget and `.global` intentionally
share the constant global key. There is no per-instance UUID. **Give distinct logical budgets
separate store namespaces**, such as different Redis prefixes or an application-owned store
adapter that frames its budget namespace before the opaque limiter key. Instances of the same
logical budget must use the same namespace, window size and rate configuration.

Persisted counters under the former raw identifiers are incompatible with the new keys.
Update any direct store inspection, seeding or administrative per-key reset tooling to use
the table above within the correct store namespace. Coordinate deployment: old and new
processes otherwise use independent counters and can admit more than the intended budget.
Quiesce old callers and let their active accounting windows expire before enabling the new
namespace, or explicitly migrate counts under a store-specific coordinated procedure. A new
empty namespace starts a fresh budget. Old per-caller counts cannot simply be renamed to one
global key without deciding how to combine usage and windows; the library does not perform
that migration.

`RateLimitScopeContractTests` checks the exact store keys for the seven strategies and four
scopes.

### Rate limiting: retained state and clocks

An identity idle for 300 seconds no longer receives a fresh budget automatically.
Cleanup retains state whenever recreation would change admission decisions.
This matters for windows longer than five minutes, slow refill, and zero refill.
Explicit `reset(identifier:)` resets one identity; `reset()` resets all budgets.
Cleanup also keeps live state when an admission or reset happens while it runs. None of
this needs a configuration change.

The first admission into an empty leaky bucket starts a new leak interval.
Fractional phase is retained while the bucket is occupied. With capacity 1 and
interval 10 seconds, an admission into an empty bucket at time 16 cannot admit
again at 20; it can at 26. `RateLimiterEvictionContractTests` compares retained
and reclaimed state for this boundary.

Local algorithms share a nondecreasing logical clock. Wall-clock rollback freezes
policy time until it catches up, so rollback cannot restore expired history or
mint quota. Distributed stores retain their own clock and expiration contract.
Adaptive token buckets retain their original capacity even when load changes.
Their identity state, and depleted zero-refill state, may remain resident until
explicit reset. No identity-count cap discards active budgets.

### Health monitoring shutdown

Copies of `HealthCheckMiddleware` share one background monitoring lifetime.
An empty `healthChecks` dictionary creates no periodic task. Releasing the last
middleware copy cancels periodic work; explicit shutdown also waits for it:

```swift
import PipelineKitResilience

func shutDownHealthMonitoring(_ middleware: HealthCheckMiddleware) async {
    await middleware.stopMonitoring()
}
```

`stopMonitoring()` is terminal for that shared background lifetime. It cancels
and joins the periodic task, including its in-flight checks and state-change
callbacks. Concurrent and repeated external stops join the same task. A check
or callback that ignores cancellation can delay shutdown indefinitely.

When a periodic check or its state-change callback calls `stopMonitoring()` on
its own middleware, stop cancels future work and returns without waiting for
itself. A later external stop still waits for that work to settle. Stop does
not disable command outcome tracking or explicit `checkHealth(for:)` calls.
Notifications originating from commands or manual checks keep their existing
asynchronous behavior and are outside the periodic shutdown guarantee.

Health status queries reevaluate retained request history and probe freshness. They scan
retained history in O(n), which is a cost on each query. Sufficient recent request failures
can take precedence over probe results.

## Cache

### Every cache needs a key generator

All four cache entry points now require `keyGenerator: any CacheKeyGenerator`:
`CachedMiddleware`, `ConditionalCachedMiddleware`, `SimpleCachingMiddleware`, and
`CachingMiddleware`. Their `.cached`, `.cachedWhen`, and `commandType:` convenience
methods require it too. `DefaultCacheKeyGenerator`, the keyless initializers, and
`useHashableKeys:` are removed. Closure callers must use `ClosureCacheKeyGenerator`;
its async closure receives the command, context, and fully qualified concrete cache
middleware type. Existing generic `CacheKeyGenerator` conformers keep their method signature.

The caller must encode **every result-varying command argument, verified principal/tenant,
and relevant configuration or result-schema version**. Authenticate and authorize before
caching a protected result. Do not substitute `hashValue`, descriptions, type names, or
correlation IDs for equality of those inputs. Include correlation only if the application's
result contract varies by correlation. Intentional shared keys are an explicit application
choice, valid only when the omitted fields cannot affect the result.

This example uses an unambiguous length-prefixed caller key. `authUserId` is written by
`AuthenticationMiddleware`; this application also establishes `verifiedTenantID` before
caching. The guards diagnose incorrect pipeline configuration instead of silently supplying
a shared identity. Extend the key whenever the command or handler gains a result-varying input.

```swift
import Foundation
import PipelineKit
import PipelineKitCache

struct ProfileQuery: Command {
    typealias Result = String
    let accountID: String
    let locale: String
}

struct ProfileStage: Middleware {
    let priority: ExecutionPriority = .preProcessing
    func execute<C: Command>(
        _ command: C, context: CommandContext, next: @escaping MiddlewareNext<C>
    ) async throws -> C.Result {
        try await next(command, context)
    }
}

let profileKeys = ClosureCacheKeyGenerator { command, context, _ in
    guard let query = command as? ProfileQuery,
          let principal = context.getMetadata("authUserId") as? String,
          let tenant = context.getMetadata("verifiedTenantID") as? String else {
        preconditionFailure("Profile caching requires a verified principal and tenant")
    }
    let fields = [query.accountID, query.locale, principal, tenant, "profile-format-v2"]
    return fields.map { "\($0.utf8.count):\($0)" }.joined()
}

let memory = InMemoryMiddlewareCache()
let bytes = InMemoryCache(maxSize: 1000)
let wrapped = CachedMiddleware(
    wrapping: ProfileStage(), cache: memory, keyGenerator: profileKeys, ttl: 300
)
let conditional = ConditionalCachedMiddleware(
    wrapping: ProfileStage(), cache: memory, keyGenerator: profileKeys, ttl: 300,
    shouldCache: { command, _ in command is ProfileQuery }
)
let simple = SimpleCachingMiddleware(
    ttl: 300, maxSize: 1000, commandType: ProfileQuery.self, keyGenerator: profileKeys
)
let encoded = CachingMiddleware(
    cache: bytes, commandType: ProfileQuery.self, keyGenerator: profileKeys, ttl: 300
)
let wrappedFactory = ProfileStage().cached(ttl: 300, cache: memory, keyGenerator: profileKeys)
let conditionalFactory = ProfileStage().cachedWhen(
    ttl: 300, cache: memory, keyGenerator: profileKeys,
    condition: { command, _ in command is ProfileQuery }
)
```

Use the unconditional wrappers only in pipelines whose commands the generator supports.
The type-selective factories and conditional false branch bypass key generation and caching.
Key generation can suspend and occurs before SimpleCachingMiddleware's synchronous storage lock.
No cache API infers a fallback identity, inspects `Hashable`, or adds correlation implicitly.

Every implementation applies the same internal framing:
`utf8Length:commandType` + `utf8Length:resultType` + `utf8Length:middlewareType` +
`utf8Length:callerKey`. Type names are fully qualified. Wrapper types include the wrapped
middleware type. Different instances of the same middleware type still need caller keys that
distinguish result-varying instance configuration. The generator's return is the caller portion,
not the complete backend key; backend per-key removal still takes the complete stored key.
`CacheIdentityContractTests` exercises all four APIs and their convenience paths.

### Invalidate existing cache contents

**Invalidate all old cache contents when upgrading**, including persistent or distributed
backends. Old keys are incompatible with the new namespace. Call `invalidateAll()` on a
`MiddlewareCache`, `clear()` on a `Cache`, and `clear()` on existing `SimpleCachingMiddleware`
instances, as applicable. TTL, cache backend interfaces, and their removal/clear semantics
remain. A deployment must also clear or version entries when result-varying application
configuration changes without an accompanying key change.

### Decompression requires an output limit

Every `CompressionUtility.decompress` call must now supply a positive `maxOutputSize`:

```swift
#if canImport(Compression)
import Foundation
import PipelineKitCache

func decodeCachedPayload(_ compressed: Data, sizeHint: Int?) throws -> Data {
    try CompressionUtility.decompress(
        compressed,
        using: .rawDeflate,
        originalSize: sizeHint,
        maxOutputSize: 1_048_576
    )
}
#endif
```

Choose the byte limit from the application's payload policy, independently of untrusted
size metadata. `originalSize` remains optional and is only a nonnegative allocation hint;
it neither defines the decoded length nor proves completion. Its initial allocation is
capped at the limit and 64 KiB, including when the hint is `Int.max`. A negative hint or a
nonpositive limit throws `CompressionError.decompressionFailed`, including for empty input.

Successful decoding returns the entire single stream, including when its decoded size
exactly equals the limit. A shorter output buffer no longer returns a successful prefix.
Output beyond the limit throws `CompressionError.dataTooLarge(maxOutputSize)`. Invalid,
truncated or stalled input and bytes following a complete stream throw
`CompressionError.decompressionFailed`; concatenated streams must be framed separately
before passing each compressed payload to this API. Invalid input must be rejected or
replaced from a trusted source rather than retried by raising the output limit. The limit
bounds returned bytes; it is not a bound on the codec's internal state or total process memory.

The utility now compresses every nonempty payload, including sizes 1–100. It no longer
returns unmarked raw bytes for those sizes. Empty input keeps its empty representation
after argument validation. Middleware still applies its configured size threshold and
uses the compressed result only when it is smaller. Old small utility outputs have no
format marker: recover them using application-owned format/size metadata or regenerate
them from trusted originals; do not infer that arbitrary failed decompression is raw data.

### Compression format names and stored labels

New writes use names that describe the actual formats:

| Previous API / stored label | New API | New stored label | Existing bytes |
| --- | --- | --- | --- |
| `.zlib` / `zlib`, `.gzip` / `gzip` | `.rawDeflate` | `deflate-raw` | Raw DEFLATE, without zlib or gzip wrappers |
| `.lzfse` / `lzfse`, `.brotli` / `brotli` | `.lzfse` | `lzfse` | LZFSE |
| `.lz4` / `lz4` | `.appleLZ4` | `apple-lz4` | Apple's framed LZ4 format |

The default is now named `.rawDeflate`; its codec is unchanged. Remove
`CompressionLevel`, `level:` and `compressionLevel:` arguments. These settings
were ignored. Encoding uses the platform's codec settings, and middleware no
longer publishes `compression.level` metadata. The new API does not advertise
gzip, Brotli, or adjustable compression levels.

Read historical labels through `LegacyCompressionAlgorithm` and
`CompressionUtility.decompressLegacy`, keeping the output limit independent of
untrusted size metadata:

```swift
#if canImport(Compression)
import Foundation
import PipelineKitCache

func readLegacyPayload(_ bytes: Data, storedLabel: String) throws -> Data {
    guard let algorithm = LegacyCompressionAlgorithm(rawValue: storedLabel) else {
        throw CompressionError.decompressionFailed("Unknown legacy compression format")
    }
    return try CompressionUtility.decompressLegacy(
        bytes, using: algorithm, maxOutputSize: 1_048_576
    )
}

func writePayload(_ bytes: Data) throws -> Data {
    try CompressionUtility.compress(bytes, using: .rawDeflate)
}
#endif
```

Deploy readers that recognize the new labels before enabling new writes in a
mixed-version system. The legacy decoder intentionally preserves the old label
mappings; a historical `gzip` label does not mean an RFC 1952 gzip stream.
Old unmarked small payloads still require application-owned metadata or
regeneration, as described in
[Decompression requires an output limit](#decompression-requires-an-output-limit).

All decoding entry points retain complete-stream and output-limit checks.
`maxCompressedSize(for:)` rejects negative input and saturates derived overflow
at `Int.max`; it is an estimate, not permission to allocate that size or a proven
bound for every codec.

## Observability

### StatsD construction and shutdown

`StatsDExporter.Configuration.useTransport` and the competing async exporter initializer
are removed. All exporters use `MetricsTransport`; the default constructor is synchronous
and lazy, and the first nonempty batch waits for readiness. Remove `useTransport:` and the
constructor's `await`; a leftover `await` on the constructor is a compiler warning, not an
error. Where startup must be validated before publishing the exporter,
install its error callback first, then call `try await exporter.start()`:

```swift
import PipelineKitObservability

func makeStatsD() async throws -> StatsDExporter {
    let exporter = StatsDExporter(configuration: .init(host: "127.0.0.1", port: 8125))
    await exporter.setErrorHandler { error in
        print("Metrics export failed: \(error)")
    }
    do {
        try await exporter.start()
        return exporter
    } catch {
        await exporter.close()
        throw error
    }
}

func useInjectedTransport(_ transport: any MetricsTransport) async {
    let exporter = StatsDExporter(configuration: .default, transport: transport)
    await exporter.setErrorHandler(nil) // Callbacks can be cleared before publication.
    await exporter.counter("synthetic.example")
    await exporter.forceFlush()
    await exporter.close()
}
```

The injected initializer takes a nonoptional, already initialized transport and transfers
its shutdown ownership to the exporter, even if no record or `start()` occurs. Concurrent
nonempty batches and explicit `start()` share one startup generation. Startup errors are
thrown by `start()` and reported through the configured callback; each failed batch reports
its terminal error. A later batch can retry failed startup. This does not automatically replay
failed batches or retry a terminal transport's failed sends. Platforms without Network report
an explicit startup error instead of silently discarding default-exporter metrics.

`close()` immediately rejects later recording through the callback, discards buffered
unsent records, cancels the exporter's flush timer and startup, and waits for their settlement
and transport shutdown. A transport produced after close begins is closed by that startup's
owner; repeated/concurrent close shares the same settlement. A cancellation-insensitive factory
or transport can delay close indefinitely. A close called from a currently active exporter
operation invalidates the exporter without waiting for that same operation to finish; its
caller can then settle. A task descendant whose originating operation has already ended
follows ordinary close settlement.

**To attempt delivery of buffered records, quiesce and join producers, call `forceFlush()`,
then `close()`.** Closing discards unsent buffers. UDP completion does not acknowledge
remote delivery, and concurrent producers are not covered by a global delivery barrier.

`MetricAggregator.forceFlush` cancels its private timer without joining it. An already
in-flight caller-owned aggregation retry can repopulate its buffer after exporter close.
Exporter closed guards prevent transport revival and post-close sends, but close is not a
barrier for caller-owned recording or full aggregator quiescence.

The default configuration still disables aggregation.

### Metrics configuration

Replace writes to `Metrics.storage`, `Metrics.exporter`, and `Metrics.errorHandler` with one
`await Metrics.configure(Metrics.Configuration(...))` call. The read-only
`Metrics.configuration` property returns a complete snapshot. `Metrics.configure(with:)`
now requires `await`; it and the host/port convenience preserve the captured storage and
error handler while replacing the exporter. StatsD callbacks are installed or cleared before
publication. Custom recorders remain responsible for their own error reporting.

```swift
import PipelineKitObservability

func configureMetrics(_ exporter: any MetricRecorder) async {
    let storage = MetricsStorage()
    await Metrics.configure(.init(storage: storage, exporter: exporter, errorHandler: { error in
        print("Metrics export failed: \(error)")
    }))
    await Metrics.counter("requests")
    await Metrics.flush()
}

func replaceRecorder(_ replacement: any MetricRecorder) async {
    await Metrics.configure(with: replacement)
    let current = Metrics.configuration
    _ = await current.storage.getAll()
}
```

A record retains one complete configuration across storage and export. Already started work
may finish on a retired configuration. Replacement does not close exporters; callers retain
and explicitly flush/close an old exporter when required. A configuration snapshot does not
clone referenced objects: intentionally reusing a mutable recorder across configurations also
shares its buffered data and callback state. `Metrics.disable()` replaces only the exporter;
local recording and the configured error handler remain available.

`Metrics.flush()` drains the captured storage and invokes `flush()` on a captured
`FlushableMetricRecorder`, without calling `record` again on the drained snapshots. Custom
recorders that need a flush operation should conform to `FlushableMetricRecorder` and implement
`func flush() async`. Nonflushable recorders still receive records at recording time, and
facade flush only drains their local storage. StatsD's new public `flush()` forwards to
`forceFlush()`; both retain the delivery and shutdown limits described in
[StatsD construction and shutdown](#statsd-construction-and-shutdown).

Flush is not a barrier for concurrent records and does not flush retired exporters. If a caller
needs a complete flush across reconfiguration, it must quiesce and join its producers, retain
and explicitly flush each relevant exporter, and then close those it owns.

### Series identity and limits

A series consists of its name, kind, unit, and exact tag dictionary. Different
label values, kinds, and units no longer merge. Raw history is retained per
series, rather than per name. Dictionaries containing punctuation remain distinct
internally; each wire format applies its own label rules at export.

`MetricsStorage` and `PoolObservability` admit at most 1,000 series by default.
Configure a larger cap for a known workload. At capacity, existing series can
still update; observations for new series are rejected and counted. These counts
measure rejected observations, not distinct rejected identities. A zero cap
disables admission. Negative capacities are invalid.

```swift
import PipelineKitObservability

let telemetryStorage = MetricsStorage(maxSnapshotsPerMetric: 100, maxSeries: 2_000)
await telemetryStorage.record(.counter("requests", tags: ["route": "/users"]))
let telemetryDiagnostics = await telemetryStorage.diagnostics
print(telemetryDiagnostics.droppedSeries)
```

### Prometheus scrape state

`export()` and `exportAggregated()` now return the same cumulative scrape view:
counter totals, latest gauges, and histogram totals with a `+Inf` bucket. Timers
remain latest-value gauges in milliseconds. No finite histogram bucket boundaries
are inferred. Use a monitoring backend with raw observations when detailed bucket
distributions are needed.

Raw history eviction, `drain()`, and `pruneOlderThan(_:)` leave scrape state intact.
`clear()` resets raw history, scrape totals, admitted identities, and diagnostics.
Thus `Metrics.flush()` no longer implicitly resets Prometheus counters by draining
its raw storage. History percentile gauges remain available from `aggregate()`.

Nonfinite observations are rejected. Finite negative counter deltas remain in raw
history but are omitted from cumulative Prometheus counters and counted in
`rejectedPrometheusUpdates`; overflowing cumulative updates follow the same rule.

Names use the legacy Prometheus text identifier grammar, preserving dot/dash to
underscore normalization. Invalid labels and collisions after normalization,
suffixing, or generated distribution naming are omitted with diagnostics. Every
series participating in a collision is rejected, so arrival order does not decide
which meaning wins. Empty-valued labels are treated as absent for collision checks.
Explicit timer units other than `ms` are rejected rather than relabeled.

The example below needs `import PipelineKitObservability`:

```swift
let scrapeStorage = MetricsStorage(maxSnapshotsPerMetric: 1)
let prometheus = PrometheusExporter(metricsStorage: scrapeStorage)
await scrapeStorage.record(.counter("requests", value: 2))
await scrapeStorage.record(.counter("requests", value: 3))
_ = await scrapeStorage.drain()
let scrape = await prometheus.exportWithDiagnostics()
print(scrape.text) // requests_total remains 5 after draining history.
print(scrape.rejectedSeries.count)
await scrapeStorage.clear()
```

### StatsD aggregation and sampling

The exporter owns both batching and aggregation deadlines. Scheduled aggregation
now transmits its output; canceled deadlines cannot drain a later interval.
Counter and gauge updates can replace existing entries when the aggregation
buffer is full, because those updates do not add stored observations.

Sampling still selects complete metric names deterministically. It does not select
independent events, and compensation is not an accuracy guarantee for a particular
name. Direct counters carry their original amount and `@rate`; aggregated counters
are compensated locally and sent without a second receiver adjustment. Timer and
histogram observations retain their sampling rate. Gauges carry no rate marker.
Negative absolute gauges use the StatsD reset-to-zero plus signed-update encoding
in one datagram.

Malformed DogStatsD tags are reported through the exporter error handler. Metric
names and prefixes cannot inject newline-delimited extra records. Nonfinite
observations and arithmetic overflow are rejected without changing an existing
aggregate. Configuration rejects nonfinite sampling/jitter and invalid capacities
or time intervals; finite sampling/jitter values retain their existing clamping.
Zero flush intervals request an immediate deadline.

Only counters accept an absent value as an increment of one. Timers accept `ms`
or a legacy absent unit; an explicitly different unit is rejected. An aggregation
window rejects new definitions that alias an existing StatsD wire name/kind/tags
after normalization, retaining the existing definition. Units are not encoded by
StatsD: choose distinct protocol names for distinct units, including across windows
and when aggregation is disabled.

Calling `ObservabilitySystem.enableStatsD(...)` again replaces its event bridge,
attempts to flush, and closes the retired exporter. `disableStatsD()` removes only
that route and likewise flushes then closes its exporter; local storage and logging
continue. The event route switches atomically before retired transport shutdown.
Calls overlapping a replacement
may finish against the exporter they already captured. Await configuration before
emitting events that must use the new endpoint.

### Metrics connections on EventHub

The hub now retains connections created by `connectMetrics`, including the
bridge and recorder. Capture its discardable UUID to disconnect explicitly:

```swift
import PipelineKitObservability

let metricsHub = EventHub()
let metricsStorage = MetricsStorage()
let metricsConnection = await metricsHub.connectMetrics(metricsStorage)
// Use the hub while the connection is needed.
await metricsHub.disconnectMetrics(metricsConnection)
```

Existing calls that ignore the result still compile and now keep the connection
until hub destruction. Each call creates an independent connection. Disconnect
is idempotent, including for unknown identifiers. Ordinary `subscribe` calls
remain weak and still require caller ownership of their subscribers.

Disconnect excludes the connection from delivery snapshots admitted afterward.
Delivery already admitted may finish and retain the bridge and recorder until
settlement. Disconnect does not join delivery, so a recorder may disconnect
itself from its callback. A synchronous fire-and-forget emit is admitted when
its delivery task reaches the hub, which may be later than the emit call.
Neither disconnect nor hub destruction flushes or closes a recorder/exporter;
its owner remains responsible for those operations.

### Trace retention

`ExecutionTracer.maxTraces` is now an enforced identity cap. At capacity, existing
traces remain writable and new trace identities are rejected; inspect
`droppedTraceCount`. Zero disables trace admission. Expired traces are removed
before new spans are recorded, independently of whether capacity has been reached.
`clearAllTraces()` also resets rejection counts. Reusing a completed trace marks it
active until the newly added span finishes. The trace-count cap does not limit the
number of spans in an admitted trace.

### Unit conversions

Timer snapshots convert seconds to milliseconds once. Pool latency conversion includes whole
seconds, clamps negatives to zero and saturates at UInt64.max, including Duration values whose
whole seconds exceed Int64.max.

## Pooling

### Pool telemetry

Pool histogram and summary percentiles now use the most recent 1,000 observations
by default. Their count and sum are cumulative; histogram minimum, maximum, and
mean also cover the lifetime since reset. Changing the window changes percentiles,
not cumulative totals. Pool distributions export as Prometheus summaries because
their API provides quantiles rather than finite histogram buckets.

```swift
import PipelineKitPooling

let poolTelemetry = PoolObservability(maximumSeries: 2_000, distributionWindowSize: 1_000)
await poolTelemetry.recordHistogram("pool_latency_ms", value: 2, labels: ["pool": "requests"])
let poolSnapshot = await poolTelemetry.captureSnapshot()
let poolScrape = poolSnapshot.prometheusFormatWithDiagnostics()
print(poolScrape.text)
print(poolScrape.rejectedSeriesCount)
```

Snapshot dictionary keys now quote and escape labels; use the snapshot's structured
labels and export methods instead of parsing the old ambiguous `name{key=value}`
encoding. `reset()` clears telemetry and admission diagnostics.

The constructor above configures an independent instance. Automatic `ObjectPool`
instrumentation still records into `PoolObservability.shared`, which uses the
default limits described in [Series identity and limits](#series-identity-and-limits).

`statsdFormatWithDiagnostics()` returns `datagrams` and `rejectedSeriesCount`;
`statsdFormat()` returns the same datagrams. Cumulative counter snapshots are
gauges, so repeated snapshots do not count the same increments again. Histogram
snapshots export `_count`, `_sum`, `_mean`, `_min`, `_max`, `_p50`, `_p95`, and `_p99`
gauges. Summaries export `_count`, `_sum`, `_p50`, `_p90`, `_p95`, `_p99`, and `_p999`
gauges. These replace the previous timer observation containing a histogram mean.
Labels use DogStatsD tags; invalid names/labels and conflicting generated metric
names are rejected as whole source series. Preserve each returned string as one
datagram: a negative gauge contains its reset and update on consecutive lines.

Invalid nonfinite observations and overflowing gauge/distribution sums are rejected
without changing the old values or consuming a new series slot; inspect
`invalidObservationCount`. Integer counter additions saturate and increment
`saturatedCounterCount`.

### Collector stop and restart

`PoolMetricsCollector.stopCollecting()` clears its history, registered exporters,
and allocation-rate baseline. **Register exporters again before restarting it.**
`PoolObservability.stopExporting()` preserves registered exporters and metrics.

Collection/export stop invalidates its current generation before suspension. Old
collection results cannot repopulate history or start another exporter after a
stop/restart. An exporter callback already running may finish; stop does not await
that callback, which permits a callback to stop its own collector. Dropping an idle
collector releases it and unregisters its owned memory-pressure callback. The
shared memory-pressure monitor has a separate lifetime.

`PoolRegistry` starts maintenance when a pool is registered; reading registry statistics
does not. The public synchronous `PoolRegistry.shutdown()` keeps its 100 ms best-effort wait
and may return before maintenance settles.

## Test support

These changes are in `PipelineKitTestSupport`.

### TestPipeline interception

Use `PipelineTestUtils.createTestPipeline(handler:middleware:)` to create a
`TestPipeline` with middleware interception. An arbitrary pipeline wrapped with
`TestPipeline(basePipeline:)` supports execution recording; attempts to configure
interception throw `TestPipelineError.interceptionUnavailable`.

Replace the former untyped mock closure with
`try await pipeline.mockMiddleware(MyMiddleware.self, for: MyCommand.self) { command in ... }`.
The closure accepts `MyCommand` and returns `MyCommand.Result`. The middleware type
must be registered with the factory, and the command type must match its handler.
An unknown middleware throws `TestPipelineError.middlewareNotFound`; a mismatched command
type throws `TestPipelineError.commandTypeMismatch`.

Add `try` to `delayMiddleware(_:delay:)` and `failMiddleware(_:after:)` calls.
Delays must be finite, nonnegative, and representable in nanoseconds; failure counts
must be nonnegative. `after: n` permits the first `n` matching middleware entries,
then injects a failure on every later entry until reset or reconfiguration. Repeated
instances of the same middleware type share the count.

Interception applies a cancellable delay first, then failure injection, then the
mock or original middleware. A mock returns in place of the selected middleware
and its downstream chain. Inactive conditional middleware does not enter interception.
`reset()` clears settings and creates a recorder for new executions; already admitted
executions retain their settings and finish recording in their original recorder.

`TestPipeline` finishes the progress reporter explicitly attached to its invocation's
`CommandContext` on success, failure, or cancellation before admission. A reporter
inherited from a parent execution remains open for that parent.

When NextGuard warnings are enabled, `TestPipeline` preserves missing-`next`
diagnostics from original middleware executed without a mock. Actual mocks and
injected failures do not produce those warnings. Original explicit warning
suppression and `UnsafeMiddleware` behavior are preserved.

### Delay helpers

Shared delay helpers now reject negative, nonfinite, or nanosecond-unrepresentable
delays with `TestPipelineError.invalidDelay`: `AsyncTestCommand.execute()`,
`AsyncTestCommandHandler.handle`, `DelayMiddleware` (including
`MockMiddlewareFactory.delay` and `simulatingTimeout`), and
`MockCommandProcessor.process`. The nonthrowing
`MockEventSubscriber(processingDelay:)` initializer enforces the same constraint
as a precondition for non-nil delays; `nil` disables its delay. Zero is allowed,
and positive delays below one nanosecond truncate to zero. These helpers keep their
public signatures.

### TimeoutTester

`TimeoutTester.withTimeout` creates a `PipelineError.timeout` when its own timer
wins. Operation errors, including operation-thrown timeouts, pass through unchanged.
`expectTimeout` returns `true` only for that
owned deadline; operation-thrown timeout or cancellation returns `false`.
Both helpers cancel and join the losing child. Work that ignores cancellation
can delay return indefinitely, so these helpers are not process watchdogs.

All `TimeoutTester` duration inputs must be finite, nonnegative, and representable
in nanoseconds. Derived durations must also fit: `operationThatWillTimeout(after:)`
adds one second, while `operationThatCompletesJustInTime(before:)` uses 80 percent
of the supplied duration. Invalid inputs fail a precondition before conversion.

### TestSynchronizer

Use `try await synchronizer.waitForSignal(checkpoint)` when successful return must
mean a signal was received. It throws native `CancellationError` on task
cancellation or `reset()`. The compatibility method `wait(for:)` returns on any
of signal, cancellation, or reset, so its return alone is not an acknowledgement.
A signal and cancellation racing after registration are settled
by the actor's processing order.

## Numeric input rules

Validate configuration from files, networks, or user input before constructing
these APIs. Nonthrowing configuration APIs use preconditions for programmer
errors; they do not silently repair invalid values. Throwing store methods use
their existing validation errors. Derived arithmetic is bounded separately.

| Surface | Accepted behavior |
| --- | --- |
| Admission / semaphore waits | `nil` is unbounded; finite nonpositive timeouts do not wait; positive timeouts are at most 86,400 seconds. Zero AsyncSemaphore capacity remains valid. |
| General timeouts | Finite nonpositive values fail immediately without launching the operation. Positive durations must be representable as UInt64 nanoseconds. Grace periods are nonnegative. |
| Retry delays | Configured delays are finite, nonnegative, and representable; multipliers are finite and nonnegative, and jitter is in 0...1. Derived backoff saturates; final jitter also respects the configured maximum. The legacy RetryPolicy requires at least one attempt; RetryMiddleware still permits zero retries. |
| Periodic work | Intervals must be finite, positive, representable, and at least one nanosecond after conversion. This covers health checks and pool cleanup, collection, and export intervals. |
| Rate limiting | Floating-point capacities/refill rates are finite and nonnegative; integer counts are nonnegative. Windows/leak intervals are finite and positive. Negative or nonfinite costs are denied before consuming or replenishing budget. Zero costs and zero refill remain supported. Adaptive factors must produce finite, nonnegative capacity. |
| Health checks | Success-rate thresholds are finite and in 0...1; count thresholds and response-time limits are nonnegative. Custom check timeouts are also validated before sleeping. |
| Pool configuration | Fractional cleanup/shrink intervals retain their precision. Shrink intervals are finite and nonnegative. History capacity zero retains no samples; negative capacity is invalid. Shrink percentages must be finite and retain the existing clamp to 0...1. |

The 24-hour limit applies to admission waits only. Other nanosecond-based timers
retain their representable range (approximately 584 years). A finite duration is
still invalid if conversion would overflow. Huge valid rate capacities saturate
integer status values; counter overflow fails closed rather than admitting more
work.

## What 0.6.0 does not promise

0.6.0 does not add any of the following:

- Hard deadlines for handlers that ignore cancellation, or preemptive cancellation. Timeouts,
  admission deadlines and retry budgets are cooperative.
- Durable execution or exactly-once side effects.
- Invalidation fencing for cache fills that are in flight, or single-flight cache fills.
- Key-memory zeroization.
- Authenticated type or encoding hints on encrypted result fields.
- Acknowledgement of UDP metric delivery, or a flush that is a barrier against concurrent
  producers.
- A metrics dashboard, a general-purpose allocation profiler, or built-in rate limiting in
  `BackPressureMiddleware`.
